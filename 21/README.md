# Система бронирования гостиницы (лабораторная работа №21, вариант 4)

Итоговый проект: законченное приложение на FastAPI с базой данных, слоистой
архитектурой, авторизацией, тестами, контейнеризацией и CI.

## Назначение

Сервис автоматизирует работу гостиницы: ведёт номерной фонд, оформляет
бронирования с проверкой пересечения периодов, принимает оплату и возвраты,
разграничивает права гостя и администратора и формирует сводную статистику.

## Функциональность

- управление номерным фондом (создание, изменение, изменение статуса, удаление);
- каталог номеров с фильтрацией по типу, статусу, цене, этажу и вместимости и сортировкой;
- подбор свободных номеров на период с исключением пересекающихся бронирований;
- создание и отмена бронирований с расчётом стоимости проживания;
- частичная и полная оплата бронирования, возврат средств;
- завершение проживания администратором (только для оплаченного бронирования);
- роли `USER` и `ADMIN` с разными правами, аутентификация по JWT;
- сводная статистика: выручка, возвраты, средняя стоимость и длительность, популярный тип номера;
- проверка работоспособности `GET /health`, журналирование HTTP-запросов и ошибок;
- автоматическая документация OpenAPI (`/docs`, `/redoc`).

## Архитектура

```
        Клиент (HTTP)
             │
             ▼
   app/api  ── роутеры, зависимости, обработчики ошибок
             │
             ▼
 app/services ── бизнес-правила, права доступа, расчёты
             │
             ▼
 app/repositories ── запросы через SQLAlchemy ORM
             │
             ▼
      PostgreSQL / SQLite
```

Модель данных: `User 1─* Booking *─1 Room`, `Booking 1─* Payment`.
Первичные и внешние ключи, ограничения `check` на период проживания, количество
ночей, положительные цены и суммы платежей, уникальность email и номера комнаты.

## Стек технологий

Python 3.11+ (проект проверен на 3.12 и 3.13), FastAPI, Pydantic v2, SQLAlchemy 2,
PostgreSQL (в тестах — SQLite), PyJWT, pytest + pytest-cov, Ruff, Docker, Docker Compose,
GitHub Actions.

## Требования

- Python 3.11 или выше;
- Docker и Docker Compose (для контейнерного запуска);
- PostgreSQL не требуется локально: по умолчанию используется SQLite.

## Установка и настройка

```bash
python -m venv .venv
.venv\Scripts\activate          # Windows
pip install -r requirements.txt
copy .env.example .env          # и заменить пароли/секреты
```

Все настройки читаются из переменных окружения (см. таблицу ниже).
Секреты в репозитории не хранятся: `.env` исключён из Git и из контекста сборки.

## Запуск

Контейнерный запуск (приложение + PostgreSQL):

```bash
docker compose up --build
```

Локальный запуск без Docker:

```bash
uvicorn app.main:create_app --factory --reload
```

Проверка: `http://localhost:8000/health`, документация `http://localhost:8000/docs`.
Сквозной демонстрационный сценарий: `python -m scripts.demo_scenario`.

## Запуск тестов

```bash
python -m pytest
python -m pytest --cov=app --cov-report=term-missing
```

Порог покрытия 70 % задан в `pytest.ini` и проверяется в CI.

## API

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `GET /health` | состояние сервиса и БД | все |
| `POST /auth/register` | регистрация гостя | все |
| `POST /auth/login` | вход, выдача JWT | все |
| `GET /auth/me` | текущий пользователь | авторизованные |
| `GET /users`, `GET /users/{id}` | список и карточка пользователя | ADMIN |
| `POST /users` | создание пользователя с ролью | ADMIN |
| `GET /rooms` | каталог: фильтры, сортировка, страницы | все |
| `GET /rooms/available` | свободные номера на период | все |
| `GET /rooms/{id}` | карточка номера | все |
| `POST /rooms` | добавить номер | ADMIN |
| `PATCH /rooms/{id}` | изменить номер | ADMIN |
| `PUT /rooms/{id}/status` | изменить статус номера | ADMIN |
| `DELETE /rooms/{id}` | удалить номер | ADMIN |
| `POST /bookings` | создать бронирование | авторизованные |
| `GET /bookings` | список бронирований (гость — только свои) | авторизованные |
| `GET /bookings/{id}` | карточка бронирования | владелец или ADMIN |
| `POST /bookings/{id}/cancel` | отмена бронирования | владелец или ADMIN |
| `POST /bookings/{id}/complete` | завершение проживания | ADMIN |
| `POST /payments` | оплата бронирования | владелец или ADMIN |
| `GET /bookings/{id}/payments` | платежи по бронированию | владелец или ADMIN |
| `GET /payments` | все платежи | ADMIN |
| `POST /payments/{id}/refund` | возврат средств | ADMIN |
| `GET /reports/summary` | сводная статистика | ADMIN |

Формат ошибок единый:

```json
{
  "error": "BOOKING_OVERLAP",
  "message": "Период пересекается с существующим подтверждённым бронированием",
  "details": {"room_id": 3, "conflicting_booking_id": 7}
}
```

Используются коды `400`, `401`, `403`, `404`, `409`, `422`, `500`, `503`.

## Бизнес-правила

1. Период бронирования должен быть корректным: дата выезда позже даты заезда, не более 365 ночей, дата заезда не в прошлом.
2. Бронировать можно только существующий номер в статусе `available`.
3. Запрещено пересечение периодов подтверждённых бронирований по одному номеру (полуинтервалы `[заезд, выезд)`).
4. Стоимость бронирования рассчитывается только сервером: число ночей × цена за ночь.
5. Сумма платежей не может превышать стоимость бронирования; оплата отменённого бронирования запрещена.
6. Отмена оплаченного бронирования запрещена до оформления возврата средств.
7. Завершить проживание можно только для полностью оплаченного бронирования.
8. Номер с активными бронированиями удалить нельзя.
9. Гость видит и изменяет только свои бронирования; административные операции недоступны роли `USER`.

## Переменные окружения

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `DATABASE_URL` | строка подключения | `sqlite:///./data/hotel.db` |
| `JWT_SECRET` | секрет подписи токенов | значение для разработки |
| `JWT_ALGORITHM` | алгоритм подписи | `HS256` |
| `ACCESS_TOKEN_TTL_MINUTES` | срок жизни токена | `60` |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | администратор при первом запуске | не создаётся |
| `LOG_LEVEL` | уровень журналирования | `INFO` |
| `SQL_ECHO` | вывод SQL-запросов | `false` |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | параметры контейнера БД | см. `.env.example` |

## CI

`.github/workflows/ci.yml` при `push` и `pull_request` выполняет три задачи:
статический анализ Ruff, тесты с покрытием (порог 70 %) и сборку Docker-образа.
Ошибка на любом шаге останавливает pipeline: `tests` зависят от `lint`,
`docker-build` — от `tests`.

## Ограничения проекта

- миграции не используются: схема создаётся вызовом `create_all` при старте;
- уровень сложности A (монолит): Redis, брокер сообщений и микросервисы не применяются;
- денежные суммы хранятся как `float` с округлением до копеек — для промышленной
  эксплуатации предпочтителен тип `numeric`;
- уведомления гостям не отправляются, статус бронирования изменяется только через API.
